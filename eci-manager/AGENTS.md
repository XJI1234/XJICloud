# eci-manager Agent 规则

本文是 `eci-manager/` 的执行规则。详细架构、API、联调结论和历史上下文见 [AGENT_CONTEXT.md](AGENT_CONTEXT.md)；人类使用文档见 [README.md](README.md)、[docs/设计与使用说明.md](docs/设计与使用说明.md) 和 [docs/测试说明.md](docs/测试说明.md)。

## 项目边界

- 这是独立的 Spring Boot 3.3.5 / Java 17 服务，端口为 `8081`，通过阿里云 ECI OpenAPI 管理容器实例。
- 本任务范围默认限于 `eci-manager/`；不要修改 `backend/`，除非用户明确要求。
- 不要扩展当前非目标：训练队列、Worker 注册/心跳、自动扩缩、独立 Node/React 前端、业务回调、镜像注册表、批量提交、运行时 Provider 热切、以及 8081 多钥目录。
- 本地操作台（`src/main/resources/static/`，无构建步骤）已在范围内。不要把 Api-Key、AccessKey 或 Secret 写入静态文件、文档或日志。

## 必须保持的不变量

- 本地实例状态是权威状态；创建是异步受理，必须先落库再进入异步调云；关闭语义是删除实例。
- 一个任务只对应一个实例。任务成功必须同时满足云侧 `Succeeded` 和本地实例已 `TERMINATED`。
- 手动实例不进入任务生命周期自动删除；任务实例由生命周期 watcher 管理。
- `Failed` 和 `TIMEOUT` 的处理顺序固定为：抓取容器日志尾部 → 持久化失败状态和日志 → 可选宽限 → 删除实例。抓日志失败不能阻断删除。
- 当前钥按 resource 各一把并持久化热切；成对 AK 走 `STATIC_AK`。`.env` 只作初始化种子，Java 不直接读取 `ALIBABA_CLOUD_*`。

## 安全与配置

- 不要把长期 AccessKey、Secret、HTTP Api-Key、`application-local.yml` 或其他凭据写入 Git、日志、测试输出或本文档。
- GET、API 响应和日志不得暴露 Secret。不要把 AK/SK 注入 ECI 容器；任务输出存储使用预签名 URL。
- 真云 ECI 任务访问 OSS 必须使用对应地域的内网 endpoint；真云测试会产生费用，测试完成后必须删除或取消实例并确认无残留。
- 需要凭据的真云联调使用 `.env` 和 `scripts/load-env.sh`；优先使用现有脚本，不要在文档中写入真实密钥。

## 模型与任务路由

本章节定义 `eci-manager` 的 Codex 协作协议。角色配置位于 [`.codex/config.toml`](.codex/config.toml) 与 [`.codex/agents/`](.codex/agents/)；从 `eci-manager/` 启动 Codex 才会加载这些项目级配置。用户指令优先于本文。

### 1. 角色与模型档位

| 角色 | 模型 | 职责 |
| :--- | :--- | :--- |
| **主 Agent** | gpt-6-sol high | 初始 Codex 会话；确认需求、编写计划、定义验收标准、拆分依赖、标注风险、汇总结果；不写实现代码。 |
| **测试 Agent** (`eci_test_author`) | gpt-6-luna xhigh | 按需求编写必要测试；严格 TDD 时还负责最小可编译骨架；单任务。 |
| **实现 Agent** (`eci_implementer`) | gpt-6-luna xhigh | 按已确认契约实现代码并验证；不改测试；单任务。 |
| **审查/裁决 Agent** (`eci_reviewer`) | gpt-6-sol high | 独立语义审查、技术裁决；只读、单任务。 |

各角色的要求：

**主 Agent**

- 定义任务与验收标准后，让 Codex 依据本节和角色描述选择子 Agent、等待结果并汇总；不设独立调度 Agent。
- 不写实现代码；根据子 Agent 简报处理阻塞、审查结论与最终汇报，不持续监控其内部过程。

**Codex 协作**

- 项目 TOML 定义可选角色与模型，不会自动启动常驻 Agent。由 Codex 主会话按适用的本文件指令启动子线程、传递任务、等待并汇总结果，无需专门的调度角色。只有拿到实际子线程 ID 和返回结果，才能声称该角色已执行；空目标的等待不算启动成功。
- 互不依赖的任务可并行；同一任务的测试、实现和审查按依赖顺序进行，避免共享工作区写入冲突。
- 汇总同一阶段的实现成果后统一交给独立审查 Agent，避免一步一审。需要测试的任务由测试 Agent 负责测试；严格 TDD 任务先写测试和最小骨架，再由实现 Agent 写代码。

**测试与实现 Agent**

- 单任务：只接收当前任务所需的上下文与契约路径，不继承无关历史。
- 不得继续派发子 Agent；不得审查自己的产出。测试 Agent 只对需求写测试，实现 Agent 不改测试。

**审查/裁决 Agent**

- 单任务：只包含能理解任务的最小上下文，与产出者分离；不写实现代码。

### 2. TDD 强制执行（TDD Enforcement）

计划标记为严格 TDD 的任务按 superpowers 技能包执行完整流程；其他任务按风险编写必要测试，不强制完整 TDD 流程。

- TDD 的执行由主 Agent 在制定计划时确定：主 Agent 应当在计划中**注明哪些子任务需要严格 TDD**，且**只对复杂任务进行要求**，其余任务不做要求。
- 审查 agent 应当对特定任务进行 TDD 流程的裁定，未提供充足证据者打回。对于没有 TDD 要求的任务，审查 agent **不得**因为流程不规范等原因而打回。
- 如果需求很简单，简化TDD流程是被允许的，但是必须向用户报告。

### 3. 契约锁定（Immutable Spec）

- 人类确认的需求文件与测试用例锁定为"契约"，所有 agent 只有读取与执行权；需要变更时上报主 agent，由人类重新确认。
- 测试失败时只允许修改实现，禁止以任何方式改动测试来变绿（放宽或删除断言、删除用例、用 mock 绕开真实逻辑、吞掉异常）。如果怀疑测试本身有误，必须上报用户来确认，不得擅自修改测试。

### 4. 质量门、熔断与降级

- 提交审查前必须依次通过项目实际配置的 lint（若有）、编译与自动化测试，任何一项未通过都直接回到修复循环，不触发语义审查。
- 语义审查不运行代码，只基于 git diff 推演边界条件与契约违例；结论必须给出文件、行号与可执行的修改建议；每个任务保留可独立审查的 diff，不自动提交 commit。
- 能用静态工具判定的问题不允许用自然语言讨论；禁止主观评判，如"不够优雅""写法太复杂"。
- **同一任务的"修复—重审"循环上限为 3 轮**；达到上限仍未通过时，主 Agent **必须停止该任务**并向人类报告未通过项与分歧点，禁止继续重试；无论是哪一种内容的审查，**只要是在同一个子任务下，都计入熔断次数**，不得变相重复审查。

### 5. 协作与通信

- 子 Agent 的任务说明只包含当前任务所需的接口、契约路径与输出要求；不粘贴历史对话、累积摘要或其他任务的产物。
- 子 agent 必须返回**纯 JSON**（不得用 markdown 代码块包裹，不得返回大段日志或完整代码）。但允许在 JSON 中通过 `summary` 字段提供简明扼要的结论，并通过 `issues[].snippet` 提供最小化的代码证据。如果有未解决的疑问，必须在 `status` 中标记为 `needs_context` 或 `blocked`，并附上具体的 `reason`。
- 子 Agent 遇阻时返回 blocked 或 needs_context，由主 Agent 补充上下文或调整后续协作，不得自行扩大任务范围。

## 工作方式

- 修改前先读相关源码、测试和文档；实现进度与下一步以计划文件为准。
- 本地环境先执行 `source ../.tools/env.sh`。自动化测试使用 `mvn test`，默认 Mock、不调用云。
- 真云操作优先使用 `scripts/run-hello-python.sh`、`scripts/debug-oss-smoke.sh` 和 `scripts/submit-3dgs-standard.sh`，不要随意创建长期残留资源。
- 不要自动执行 `git commit` 或 `git push`，除非用户明确要求。
