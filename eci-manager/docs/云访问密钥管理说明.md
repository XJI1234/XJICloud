# 云访问密钥管理说明

本文说明 XJICloud Admin 中云 AccessKey 的新增、删除和选用流程，以及它与 `eci-manager`（8081）的关系。接口实现位于主后端 `services/backend`；本文从 `eci-manager` 使用者角度说明两边的职责。

## 1. 两层职责

| 组件 | 保存内容 | 职责 |
|------|----------|------|
| 主后端 Admin | 多把 AccessKey 目录、每把钥的资源绑定、每个资源当前选中的目录 ID | 管理钥的新增、编辑、删除、测试和选用 |
| `eci-manager` | 每种资源当前生效的一对 AccessKeyId / AccessKeySecret | 接收主后端推送的当前钥，落盘并热更新 ECI / OSS 客户端 |

资源目前为 `ECI_OPENAPI` 和 `OSS`。同一目录项可以绑定其中一个或两个资源；两个资源分别记录当前目录项，因此可以使用不同的钥。8081 不保存目录、不认识目录 ID，也没有新增、删除或按 ID 选钥接口。

## 2. 新增与编辑

在 Admin 中新增钥时，提交名称、完整 AccessKeyId、完整 AccessKeySecret，以及至少一个资源。主后端把一条目录记录写入 `cloud_access_key`，把资源绑定写入 `cloud_access_key_resource`。选择两个资源表示这把钥可用于两者，不会立刻切换任何资源的当前钥。

编辑可改名称、凭据和资源绑定。Secret 不会在读取响应中返回；更新时不填写凭据表示保留已存值。不能移除该钥当前正在使用的资源绑定；应先为该资源选用其他钥，再编辑绑定。

Admin 对应接口：

| 操作 | 方法与路径 | 关键约束 |
|------|------------|----------|
| 按资源列出 | `GET /api/v1/admin/cloud-access-keys?resource=ECI_OPENAPI` | OSS 使用 `resource=OSS`；列表只含绑定该资源的钥 |
| 新增 | `POST /api/v1/admin/cloud-access-keys` | `resources` 至少包含一个资源；凭据须完整 |
| 读取 / 编辑 | `GET` / `PUT /api/v1/admin/cloud-access-keys/{id}` | 响应只含脱敏 AK、是否有 Secret、资源和选中状态 |
| 草稿测试 | `POST /api/v1/admin/cloud-access-keys/test` | 使用请求中的完整凭据测试，不保存、不切换 |
| 已保存钥测试 | `POST /api/v1/admin/cloud-access-keys/{id}/test` | body 指定 `resource`；不传 AK/SK |

## 3. 选用与热切换

选用请求必须指定一个 `resource`。主后端检查目录项存在、绑定了该资源且凭据完整，然后通过带 `X-Api-Key` 的请求调用 8081：

```http
PUT /api/v1/eci/runtime-credentials
Content-Type: application/json
X-Api-Key: <eci-manager 的服务端 Api-Key>

{
  "resource": "ECI_OPENAPI",
  "accessKeyId": "<完整 AccessKeyId>",
  "accessKeySecret": "<完整 AccessKeySecret>"
}
```

8081 把该资源的当前凭据写入 `eci_runtime_config`，并立即重建对应客户端：`ECI_OPENAPI` 调用 `EciProvider.reloadAccessKey`；`OSS` 调用 `OssStorageService.applyRuntimeKeys`。Mock 模式下写入仍可成功，ECI Provider 不发起真实云连接。

8081 成功返回后，主后端才把目录项 ID 写入 `system_config` 的 `cloud.current-access-key-id.<RESOURCE>`。因此选用 ECI 不会改 OSS 的当前指针或客户端，反之亦然。HTTP Api-Key 是独立的服务鉴权配置，不属于这套云凭据，也不会随选用而变化。

这两个服务的数据库写入不构成一个分布式事务：若 8081 已应用新钥，但主后端保存当前 ID 失败，接口会报错提示重试选用。再次选用是可行的；主后端数据库中的选中状态是 Admin 目录状态，8081 的 GET 则是运行时实际持有的凭据状态。

查看当前状态：

```http
GET /api/v1/eci/runtime-credentials
X-Api-Key: <eci-manager 的服务端 Api-Key>
```

响应包含各资源的 `configured`、脱敏 `accessKeyHint` 和 `mode`，不返回 Secret。8081 的 `POST /api/v1/eci/runtime-credentials/test` 可测试草稿或当前钥，不会写库或热切客户端。Admin 页面选用前的测试走主后端的测试接口，主后端再调用该 8081 test 接口。

## 4. 删除与轮换

当前选中的目录项不能删除；若同一项正被 ECI 和 OSS 使用，两个资源都要先分别选用其他钥。删除非当前项只删除主后端目录记录，不会调用 8081，也不会撤销云端 AccessKey。若 8081 当前持有的凭据与目录状态因故不同，删除目录记录也不会改变 8081 当前凭据。

推荐轮换步骤：

1. 新增新钥，并绑定需要轮换的资源。
2. 分别用对应资源测试新钥。
3. 对每个资源单独选用新钥，确认 Admin 选中状态及 8081 当前钥 hint 已更新。
4. 只有旧钥不再被任何资源选中后，才删除旧目录项；再按云账号的凭据治理流程处理旧云钥。

资源绑定、当前选择和删除的保护都由主后端校验。`eci-manager` 只负责接受一对当前凭据；其 `.env` / properties 凭据只在对应运行时配置行不存在时作为启动种子，不能覆盖已持久化的热切结果。

## 5. 安全边界

- AccessKeySecret 不出现在主后端 API 响应或 8081 GET 响应中；AK 只以 hint 形式显示。
- 主后端调用 8081 使用服务端配置的 `eci-manager` base URL 和 HTTP Api-Key。不要把该 Api-Key 或云 Secret 放进静态操作台、URL、日志或文档示例中的真实值。
- 不要把云 AccessKey 注入 ECI 容器环境变量。OSS 任务使用预签名 URL。
- Admin API 使用管理员 JWT；8081 `/api/v1/eci/**` 使用 `X-Api-Key`。两者不可互换。
- 当前主后端密钥目录和 8081 当前凭据均直接持久化 Secret，尚未实现字段加密或外部 Secret Store。数据库文件、数据库账号及备份应限制访问，不能随交付文件分发；响应脱敏不代表静态存储已加密。
